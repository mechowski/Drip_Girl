# Drip Girl — передача проекта другому ИИ-агенту

Этот файл — техническая точка входа для агента, который будет продолжать разработку. Сначала прочитайте его, затем `README.md` и файлы из раздела «Карта проекта». Не считайте интерфейсный прототип серверной производственной системой: текущая версия полностью работает в браузере и хранит данные локально.

## 1. Что это за проект

Drip Girl — русскоязычное веб-приложение для учёта производства дрип-кофе:

1. Регистрация обжаренного лота.
2. Дробление веса по форматам и назначениям.
3. Расчёт дегазации и создание производственных задач.
4. Частичное или полное изготовление, списание остатка кофе.
5. Поступление на сток, резервирование и FIFO-списание.
6. Формирование наборов, отчёты сборщиков и закрытие производственного дня.
7. Административные корректировки, предупреждения, аудит и JSON-резервные копии.

- Репозиторий: `https://github.com/mechowski/Drip_Girl.git`
- Основная ветка: `main`.
- Код приложения находится в каталоге `app/`, а не в корне репозитория.
- Базовая проверенная версия перед добавлением этого документа: коммит `469eeb6` (`Применить новый дизайн Drip Girl`).
- Основной пользовательский язык и язык интерфейса: русский.

## 2. Быстрый запуск

Требования: Node.js 20 или новее. Базовая версия проверялась также на Node.js 24.22.1 и npm 11.12.1.

```bash
git clone https://github.com/mechowski/Drip_Girl.git
cd Drip_Girl/app
npm ci
npm run dev
```

Vite по умолчанию использует порт `3000`. Точный адрес смотрите в выводе команды. Для явного адреса:

```bash
npm run dev -- --host 127.0.0.1 --port 3000 --strictPort
```

Локальный пароль администратора по умолчанию: `1337`. Он меняется в админпанели. Это только локальное ограничение интерфейса, а не серверная авторизация.

Production-сборка и её локальный просмотр:

```bash
npm run build
npm run preview
```

Сборка создаётся в `app/dist/`. Это статический frontend без серверного API.

## 7. Критические бизнес-правила

### Лоты и вес

- ID сущностей создаются через `crypto.randomUUID()`.
- Вес лота и каждого назначения должен быть положительным конечным числом.
- Сумма назначений не может превышать вес лота; допуск `1e-9` защищает от ошибок плавающей точки.
- Назначения группируются в производственные задачи по `formatId`, а не по каждому назначению отдельно.
- Плановый выход: `floor((weightKg + 1e-9) / coefficient)` для каждого назначения, затем суммирование внутри задачи.
- По умолчанию в форме одно назначение, и весь вес лота автоматически подставляется в него. При одном назначении изменение веса лота синхронизирует вес назначения.

### Ввод дробного веса — не регрессировать

Поля веса намеренно используют `type="text"`, `inputMode="decimal"` и строковое состояние. Запятая заменяется точкой; разрешены пустая строка и промежуточное значение вида `0.`. Преобразование в `Number` происходит при отправке.

Не заменяйте эти поля на обычный `type="number"` и не преобразуйте значение в число на каждом нажатии: ранее это приводило к нулю при полном стирании и исчезновению значения при вводе точки. Существующие accessible names `Вес после обжарки, кг` и `Вес 1` используются в E2E.

### Дегазация и рабочие дни

- Дегазация: от 1 до 5 календарных дней.
- Если день готовности рабочий, `scheduleDecision = 'none'`, задача сразу approved.
- Если день нерабочий, производство переносится на следующий рабочий день.
- Если фактическая дегазация при таком переносе не превышает 6 дней, решение — `move`; требуется подтверждение даты.
- Иначе выбирается предыдущий рабочий день и решение `bu` — сценарий «Запаковать в Б/у».
- `workingOverrides` имеет приоритет над выходными и `nonWorkingDays`.
- Праздники и переносы хранятся локально; их нужно вручную актуализировать.

Не пишите E2E с предположением, что кнопка «Подтвердить дату» появляется всегда: это зависит от даты обжарки и календаря. Существующий тест проверяет её наличие перед нажатием.

### Производство

- Изготавливать можно только открытую задачу с подтверждённой датой.
- Количество — целое положительное число.
- Ответственный должен быть активным сотрудником.
- Каждый приход создаёт записи стока и транзакции `receipt`.
- Количество распределяется по назначениям соответствующего формата с учётом уже созданного стока.
- Задача завершается при достижении планового количества либо когда расчётный остаток кофе исчерпан.
- После изготовления интерфейс предлагает списать остаток. Полное списание остатка переводит задачу в завершённые.
- Нельзя списать больше расчётного остатка; причина списания обязательна.

Расчётный остаток: `sourceWeightKg - producedQuantity * coefficient - writtenOffKg`, с ограничением снизу нулём в `remainingCoffee()`.

### Сток, сборка и FIFO

- Доступно: `max(0, quantity - reserved)`.
- Нельзя уменьшить физический остаток ниже активного резерва.
- План сборки сохраняет снимок состава (`compositionSnapshot`): последующее отключение или изменение исходного состава не должно переписывать уже запущенное задание.
- При подтверждении плана сток повторно проверяется и резервируется атомарно.
- Резервирование и списание используют FIFO: `manufacturedAt`, затем `createdAt`, затем `id` как детерминированный tie-breaker.
- Одно задание может иметь несколько отчётов от сборщиков, пока не исчерпан план.
- Административная коррекция отчёта обязана согласованно изменить отчёт, задание, сток, резервы, транзакции и аудит.
- При закрытии дня незавершённые подтверждённые/частичные задания переносятся на следующий рабочий день вместе с остатками резервов.

Все многотабличные операции должны оставаться внутри Dexie-транзакций. Не разбивайте атомарную операцию на независимые вызовы из UI.

## 8. Данные, миграции и резервные копии

База IndexedDB: `drip-girl-production`. Текущая версия схемы: `2`.

Основные таблицы:

- лоты и производство: `lots`, `allocations`, `productionTasks`, `productionEntries`;
- сток: `inventory`, `inventoryTransactions`, `reservations`, `aliases`;
- составы: `sheetConnections`, `importedCompositions`, `manualCompositions`;
- сборка: `assemblyPlans`, `assemblyTasks`, `assemblyReports`;
- организация: `employees`, `productionDays`, `dailyReports`;
- контроль: `warnings`, `adjustments`, `auditEvents`, `settings`.

Полный список экспортируемых таблиц находится в `tableNames` в `src/persistence/db.ts`.

При изменении схемы:

1. Обновите типы и при необходимости `DEFAULT_SETTINGS`.
2. Увеличьте `SCHEMA_VERSION`.
3. Добавьте новый `this.version(N).stores(...).upgrade(...)`; не переписывайте старые версии.
4. Добавьте новые таблицы в `tableNames`, иначе они не попадут в backup.
5. Проверьте миграцию существующих данных и импорт старой резервной копии.
6. Добавьте модульные тесты.

`importBackup()` полностью заменяет локальные данные внутри транзакции. Не вызывайте его как скрытый побочный эффект и не удаляйте пользовательские данные ради теста.

Demo-записи помечаются `isDemo`. `clearDemoData()` удаляет только такие записи и не трогает настройки. Сохраняйте это разделение.

## 9. Google Sheets

Реализация находится в `src/integrations/googleSheets.ts`.

- Поддерживаются публичные/опубликованные для чтения таблицы; доступ зависит от CORS.
- Ссылка должна содержать `/d/ID/`.
- Название листа должно содержать `×16` или `×30` (разбор допускает нахождение `16`/`30` в имени).
- Первая строка содержит названия наборов; колонки — отдельные составы.
- Для ×16 используются четыре лота по 4 дрипа по умолчанию, для ×30 — три лота по 10.
- Строка лота имеет формат `Страна / название`.
- Дополнительные строки сохраняются как метаданные.
- Неуспешный импорт не должен затирать последний успешный снимок.
- Автоматическая синхронизация в `App.tsx` запускается раз в 24 часа только пока приложение открыто.

Для реальной серверной синхронизации понадобится отдельный адаптер; интерфейс-заготовка есть в `future.ts`, но backend отсутствует.

## 12. Правила безопасной работы для агента

1. Начните с `git status --short`, `git pull --ff-only origin main` и чтения актуальных файлов. Не полагайтесь только на этот документ после новых коммитов.
2. Сохраняйте чужие незакоммиченные изменения. Не используйте `git reset --hard`, `git clean -fd` или массовую перезапись без явной просьбы.
3. Сначала воспроизведите задачу и найдите конкретную причину. Меняйте минимальный необходимый набор файлов.
4. Расчёты держите в `domain`, сохранение и транзакции — в `persistence`, отображение — в `pages`/`ui`.
5. Не обходите репозиторий прямыми изменениям таблиц из страниц, если операция затрагивает связанные сущности.
6. Сохраняйте аудит, предупреждения, транзакции стока и снимки составов там, где это требуется текущей моделью.
7. Не добавляйте backend, Docker или внешние сервисы как будто они уже существуют. Для такого расширения нужен отдельный архитектурный этап.
8. Не коммитьте реальные резервные копии, локальные данные, секреты, токены, cookies и пользовательские таблицы.
9. Перед отправкой выполните `git diff --check` и полный набор проверок для функциональных изменений.
10. В отчёте указывайте, что именно изменено, какие проверки действительно запущены и что осталось непроверенным.

## 13. Известные ограничения — это не обязательно баги

- Данные доступны только в текущем браузере на текущем устройстве.
- Очистка данных браузера может удалить производственную информацию; нужен регулярный JSON-экспорт.
- Устройства и сотрудники не синхронизируются между собой.
- Пароль администратора не заменяет серверную авторизацию и защиту данных.
- Google Sheets обновляется только при открытом приложении.
- Производственный календарь требует ручного ведения праздников и переносов.
- Нет backend, серверной БД, ролей, блокировок между устройствами и совместной работы в реальном времени.
- Битрикс, приложение обжарки, сборка со СМОЛ и автоматический структурированный учёт брака не входят в текущую версию.
- Production build может показывать предупреждение Vite о JS-чанке больше 500 КБ. Это не ошибка сборки; оптимизацию разбиения следует делать отдельно и проверять маршруты после неё.

## 14. Если задача — переход на сервер

Не переписывайте доменные формулы: они не зависят от Dexie. Заменяемый слой — репозиторий IndexedDB на API-адаптер. Серверной версии потребуются:

- настоящая авторизация и роли;
- транзакции и ограничения целостности в БД;
- защита резервов от гонок между пользователями;
- серверный аудит и история изменений;
- миграция/импорт локальных JSON-данных;
- серверная синхронизация Google Sheets;
- резервное копирование и политика хранения;
- новые интеграционные тесты на конкурентные операции.
